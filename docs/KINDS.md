# Workflow kinds

Catalogue of the workflow templates (kinds) actlith ships in v1. Read it
together with SPEC-PROMPT.md. Every kind here is in scope for building;
nothing in this file is deferred.

Shapes come from the fleet survey of 2026-10-15: pklith `ci.yml` for `gate`,
nix-hk `build.yml`, `update-pins.yml` and `upstream.yml` for the others.

## Common to every kind

- Header: `# generated by actlith gen from .actlith; do not edit`.
- `permissions: contents: read` at top level; jobs widen only what they need.
- `concurrency`: group `<id>-${{ github.ref }}`; cancel in progress for
  push / pull request kinds, never for scheduled kinds (a cancelled bump
  run can leave a half-pushed branch).
- `timeout-minutes` on every job (default 30).
- Checkout pinned by SHA, `persist-credentials: false` unless the job pushes.
- install-nix pinned by SHA, with `extra-substituters` and
  `extra-trusted-public-keys` for the row's cache (see Caches).
- Every `run:` is one line. Logic longer than one command lives in a script
  seeded into the repository (`scripts/actlith/<name>.sh`, see
  SPEC-PROMPT.md), so shellcheck, bats and xenolith see it.

## Row values

`.actlith` `## workflows` columns: `id|kind|systems|cache|args`.

- `id`: file name `.github/workflows/<id>.yml`, and the workflow `name`.
- `kind`: one of the kinds below; v1 has no repository-defined kinds.
- `systems`: nix systems, comma-separated; `-` = the kind's default.
- `cache`: a cache named in `## caches` (below), or a built-in cachix
  cache (v1: `pr0d1r2`) when no `## caches` row has that name; `-` = no
  cache steps.
- `args`: `key=value` pairs, comma-separated, validated per kind; an unknown
  key is an error, not ignored.

## Caches

`## caches`, columns `name|kind|url|key|push`, optional: pipelith's
neutral section, so the same rows work on GitLab through lablith. Each
of `url`, `key` and `push` is `-`, a literal, or `secret:NAME` (a
repository secret). pipelith checks every row; its docs/KINDS.md has the
rules for each kind.

```text
## caches
name|kind|url|key|push
example-cache|https|https://cache.example.org|example-cache-1:<base64>|secret:EXAMPLE_NETRC
hidden-cache|https|secret:HIDDEN_URL|secret:HIDDEN_KEY|-
own-cachix|cachix|-|own-cachix.cachix.org-1:<base64>|secret:OWN_CACHIX_TOKEN
private-cache|https|https://private.example.org|private-cache-1:<base64>|read=secret:PRIVATE_READ, push=secret:PRIVATE_PUSH
```

- Reading: install-nix's `extra_nix_config` gains `extra-substituters`
  (the url) and `extra-trusted-public-keys` (the key), literals as they
  are. When either is a secret, it is written as `${{ secrets.NAME }}`
  in an install-nix step that skips fork pull requests, and a second
  install-nix step without the cache runs only for them: a fork gets no
  secrets, so it builds without the cache rather than with an empty
  substituter.
- Reading a private `https` cache, one that answers only with
  credentials: `read=secret:R` in the `push` cell (alone, or beside
  `push=secret:P`) names the netrc nix reads it with. Before
  install-nix, a step that skips fork pull requests runs the seeded
  `scripts/actlith/read-netrc.sh` with `NETRC: ${{ secrets.R }}` and
  `URL` through `env:`. The script masks the url, checks that it starts
  with `https://` (a url held by a secret is known only when the job
  runs) and stops without writing anything when it does not, naming the
  cache and the secret but never the url; otherwise it writes the
  netrc with `umask 077` to `$RUNNER_TEMP/read-netrc`, which stays for
  the job's later steps and goes with the runner's temp dir. The
  trusted install-nix step adds
  `netrc-file = ${{ runner.temp }}/read-netrc`; a fork pull request
  runs without the cache. Every
  kind does this, `gate`, `build`, `update-pins` and `upstream` alike.
- Pushing, `push` is `-`: read-only, no cachix step and no push step.
  A `build` row is refused on a read-only cache, since it pushes there
  and asks it back.
- Pushing, the built-in cache: the cachix step with `CACHIX_AUTH_TOKEN`,
  as before.
- Pushing, `cachix` with `secret:NAME`: the same cachix step with
  `authToken: ${{ secrets.NAME }}`.
- Pushing, `https` with `secret:NAME`: the secret holds a netrc file for
  the cache's host, and the endpoint must accept authenticated HTTP
  `PUT`. A step runs the seeded `scripts/actlith/push-https.sh`, given
  `NETRC: ${{ secrets.NAME }}` and `URL` through `env:`. The script masks
  the url with `::add-mask::` before any output and never prints it,
  skips a run without the netrc, writes the netrc with `umask 077` to
  `$RUNNER_TEMP/netrc`, removes it on exit, and runs `nix copy --option
  netrc-file "$RUNNER_TEMP/netrc" --to "$URL"` on the outputs. `nix
  copy` uploads paths as built, so the cache signs them when it serves
  them, or they were signed upstream. `gate` copies
  `devShells.<system>.default.inputDerivation` (everything `nix develop`
  needs) before its command, skipping fork pull requests; `build`
  copies `packages.<system>.<package>` from `main` only.
- An https push needs its output in the flake: every flake is expected
  to keep a default cacheable output, so a `gate` row pushing to an
  https cache needs `devShells.<system>.default`. The script evaluates
  each output before it writes the netrc; a missing one fails the step
  with an `::error::` naming it and the fix (add it to `flake.nix`, or
  set `cache-push=false` on the row), not with nix's own error halfway
  through the copy.
- The read and push netrc stay apart: the push step gets only the push
  secret and writes its own file, passed to `nix copy` with `--option
  netrc-file`, whichever netrc nix reads the cache with.
- `actlith report` lists a url or key secret as `cache read`, a read
  netrc as `cache read (netrc)`, and the push secret as `cachix push`
  or `cache push (netrc)`.

## Own runners

`## runners`, columns `system|labels`, optional: a row moves that
system's jobs, in every row, from GitHub's hosted runner to the
repository's own runner, one carrying every listed label.

```text
## runners
system|labels
x86_64-darwin|self-hosted, macOS, X64
```

- The job runs on `runs-on: [<label>, ...]`. It is a job of its own,
  `<job>-<system>`, never an entry in the hosted matrix: a job's `if:`
  cannot read the matrix, so only a job of its own can carry the guard
  below.
- The guard: `if: github.event_name != 'pull_request' ||
  github.event.pull_request.head.repo.full_name == github.repository`.
  The job runs for a push, a schedule, a manual run or a pull request
  from a branch of this repository, never for a fork's pull request,
  whose code would otherwise run on your machine. There is no switch to
  turn it off. Hosted jobs never carry it.
- On a public repository, also register the runner to that one
  repository, and require approval before workflows from forks run.
- A fork's pull request shows the guarded job as skipped, not failed;
  it runs on the push after the merge.
- actionlint knows `self-hosted`, `macOS`, `Linux`, `X64` and `ARM64`; a
  label of your own needs its `self-hosted-runner.labels` config.

## `gate`

The hk gate on every supported system. Replaces the fleet `ci.yml`.

- Triggers: push to `main`, `pull_request`, `workflow_dispatch`.
- Job `gate` (name is stable: `pklith protect` reads it), matrix over the
  hosted systems, `fail-fast: false`. A system on an own runner gets job
  `gate-<system>`, named `gate (<system>)` so its check reads like the
  matrix's, with the same steps and the guard.
- Steps: checkout (`fetch-depth: 0`, the semver step needs tags), install-nix,
  cachix (push skipped for fork PRs, `pushFilter` keeps sources out) or the
  https push (see Caches), run the gate command.
- Default systems: `x86_64-linux`, `aarch64-linux`, `aarch64-darwin`,
  `x86_64-darwin` (on `macos-15-intel`, GitHub's last Intel image,
  available until August 2027).
- args: `command` (default `nix develop --command hk check --all --check`),
  `timeout` (job minutes, default `30`), `xcode` (GitHub only, macOS rows
  only: an Xcode version such as `26.4`), `cache-push` (set to `false` for a
  read-only cache).
- `xcode=<version>`: for a repository whose toolchain nix cannot supply
  (Swift, XCTest). The job sets `DEVELOPER_DIR` to
  `/Applications/Xcode_<version>.app/Contents/Developer`, and its first
  step fails, naming that path, when the runner image does not carry it;
  it never falls back to the image's default Xcode. It then prints
  `xcodebuild -version`, so the log records the Xcode the gate ran with.
  A row with a Linux system (the `-` default has two) is refused, and
  `actlith report` lists the Xcode beside the runner.

## `build`

Build and cache a flake package on every system, then prove the cache has it.
For packaging repositories such as nix-hk.

- Triggers: as `gate`.
- Job `build`: matrix over the hosted systems, `nix build
  --print-build-logs .#packages.<system>.<package>`; cachix push only from
  `main`. A system on an own runner gets job `build-<system>`, named
  `build`, with the same steps and the guard.
- Job `check`: `nix flake check --all-systems`. Every system has a
  runner, so none is only evaluated.
- Job `verify-cache` (needs every build job, `main` push only): every system's output
  path answers 200 from the cache. Reason: a cachix push failure does not fail
  its job. On an https cache it runs the seeded
  `scripts/actlith/verify-https.sh`, which asks `<url>/<hash>.narinfo`
  with the read netrc when the cache has one, else the push netrc when
  there is one, and never prints the url.
- args: `package` (required), `timeout` (job minutes, default `30`).

## `update-pins`

Follow `nixpkgs-lock` and propose the bump as a PR. Pull model: the consumer
polls; nixpkgs-lock holds no cross-repo token.

- Triggers: `schedule` (cron from args), `workflow_dispatch`.
- Job permissions: `contents: write`, `pull-requests: write`.
- Steps: checkout (credentials kept, it pushes), install-nix, seeded script
  `update-pins.sh`: update the input, build, push a branch
  `pins/nixpkgs-<short rev>`, open a PR; idempotent if the branch exists.
- Also runs `actlith pin` and `actlith gen` in the same branch, so action pins
  and a new actlith version arrive through the same reviewed PR.
- args: `cron` (default `50 6 * * *`, after nixpkgs-lock refreshes), `build`
  (flake attribute built before proposing; default `.#default`), `token`
  (default `GITHUB_TOKEN`, see the known limit), `timeout` (job minutes,
  default `30`).
- Known limit: a PR opened with `GITHUB_TOKEN` does not trigger other
  workflows, so the gate does not run on it until someone pushes or reruns.
  args `token` names a secret with a GitHub App or fine-grained token to lift
  this; default is `GITHUB_TOKEN` and the limit is documented.

## `upstream`

Poll an upstream release and propose the bump as a PR. Same pull model and
PR mechanics as `update-pins`.

- Triggers: `schedule` (cron from args), `workflow_dispatch`.
- Steps: checkout, install-nix, cachix read-only, the repository's own bump
  script (path from args; it prints `NEW_VERSION=` to `GITHUB_OUTPUT`), then
  the seeded `open-pr.sh`.
- args: `script` (required), `cron` (default `20 6 * * *`), `branch-prefix`
  (default `upstream/`), `token` (default `GITHUB_TOKEN`, as in
  `update-pins`), `timeout` (job minutes, default `30`).

## Not in v1

Survey one-offs (`release.yml` in 3 non-fleet repos, `format-upstream.yml`,
`publish-image.yml`, ...) stay hand-written and listed in `.actlith`
`## hand-written`. A kind is added only when two fleet repositories need it.

## Adopted services

The adopted service catalogue is specified by ownership, not by copying YAML
templates. Workflow services (CodeQL, Scorecard, release-plz, CodSpeed, Bencher,
Codecov, Semantic PR, stale, lychee and crates.io trusted publishing) are
forge-only contracts owned by `src/kind`; until two fleet repositories share a
shape they remain `## hand-written` rows. Dependabot, Renovate and Mergify
write non-workflow configuration files and are adopted catalogue entries, but
their renderers and drift checks are outside v1; their owner and declaration
path remain documented in `docs/SERVICES.md`. Harden-Runner, artifact
attestations, cache-nix-action
and flake-checker-action are typed steps owned by `src/kind`, and GitHub merge
queue is the `merge_group` trigger owned there as well. Secret scanning and
push protection are settings/API owned there. CodeRabbit, Socket and
Greptile file stubs are owned by `src/bots`; app-only services emit no file.
Every row and its free-tier/user-action rule is catalogued in
`docs/SERVICES.md` (`.:V41`).
